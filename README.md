## Session Fixation چیست؟

**Session Fixation** یک آسیب‌پذیری امنیتی است که در آن مهاجم می‌تواند شناسه نشست (Session ID) یک کاربر را از قبل تعیین کند.

### سناریوی حمله

```
┌─────────────┐     1. لینک با توکن     ┌─────────────┐
│   مهاجم     │ ──────────────────────► │   قربانی    │
└─────────────┘                         └─────────────┘
                                               │
                                               │ 2. ورود با توکن
                                               ▼
                                        ┌─────────────┐
                                        │   سرور     │
                                        └─────────────┘
                                               │
                                               │ 3. نشست با همان توکن
                                               ▼
┌─────────────┐     4. دسترسی با توکن   ┌─────────────┐
│   مهاجم     │ ◄────────────────────── │   قربانی    │
└─────────────┘                         └─────────────┘
```

### مراحل حمله:

1. **مهاجم توکنی انتخاب می‌کند** (مثلاً `EVIL_TOKEN`)
2. **مهاجم لینک را به قربانی ارسال می‌کند:**
   ```
   http://localhost:8000/vulnerable/login?token=EVIL_TOKEN
   ```
3. **قربانی روی لینک کلیک کرده و وارد سیستم می‌شود**
4. **سرور آسیب‌پذیر همان توکن را به عنوان شناسه نشست استفاده می‌کند**
5. **مهاجم کوکی خود را با همان توکن تنظیم می‌کند:**
   ```javascript
   document.cookie = "vulnerable_session=EVIL_TOKEN"
   ```
6. **مهاجم به داشبورد قربانی دسترسی پیدا می‌کند! 💀**

## نحوه اجرای حمله

### مرحله ۱: اجرای سرور

```bash
uvicorn main:app --reload
```

### مرحله ۲: باز کردن لینک آسیب‌پذیر

در مرورگر، آدرس زیر را باز کنید:

```
http://localhost:8000/vulnerable/login?token=HACKER_TOKEN_123
```

### مرحله ۳: ورود به سیستم

با اطلاعات زیر وارد شوید:
- نام کاربری: `admin`
- رمز عبور: `123456`

### مرحله ۴: بررسی شناسه نشست

در صفحه داشبورد، شناسه نشست را بررسی کنید. اگر همان `HACKER_TOKEN_123` نمایش داده شود، **حمله موفق بوده است!**

### مرحله ۵: شبیه‌سازی حمله مهاجم

مهاجم می‌تواند:

1. **در مرورگر دیگر (یا پنجره خصوصی):**
   - DevTools را باز کنید (F12)
   - به تب Console بروید
   - دستور زیر را اجرا کنید:
     ```javascript
     document.cookie = "vulnerable_session=HACKER_TOKEN_123"
     ```
   - به آدرس زیر بروید:
     ```
     http://localhost:8000/vulnerable/dashboard
     ```

2. **نتیجه:** مهاجم بدون ورود به سیستم، به داشبورد قربانی دسترسی پیدا می‌کند!

## راه‌حل امن (Session Regeneration)

### اصل کلیدی

> **پس از هر احراز هویت موفق، شناسه نشست جدید تولید شود.**

### تفاوت کد آسیب‌پذیر و امن

#### ❌ کد آسیب‌پذیر:

```python
# شناسه نشست از کوکی موجود استفاده می‌شود (بدون تغییر)
existing_session_id = request.cookies.get("vulnerable_session")
if existing_session_id:
    session_data.user_id = user.id  # فقط کاربر را متصل می‌کنیم
    session_id = existing_session_id  # ❌ همان شناسه قبلی!
```

#### ✅ کد امن:

```python
import secrets

# همیشه شناسه جدید تولید می‌شود
new_session_id = secrets.token_hex(32)  # ✅ شناسه تصادفی و امن

# نشست قدیمی حذف می‌شود
if old_session:
    db.delete(old_session)

# نشست جدید ایجاد می‌شود
new_session = SessionData(session_id=new_session_id, user_id=user.id)
```

### پرچم‌های امنیتی کوکی

```python
response.set_cookie(
    key="secure_session",
    value=new_session_id,
    httponly=True,      # جلوگیری از دسترسی JavaScript
    samesite="lax",     # محافظت در برابر CSRF
    secure=True         # فقط HTTPS (در تولید)
)
```

### تست نسخه امن

1. آدرس زیر را باز کنید:
   ```
   http://localhost:8000/secure/login?token=HACKER_TOKEN_123
   ```

2. وارد سیستم شوید.

3. **نتیجه:** شناسه نشست کاملاً متفاوت از `HACKER_TOKEN_123` خواهد بود!

## 🔒 نکات امنیتی

| نکته | توضیحات |
|------|---------|
| Session Regeneration | همیشه پس از ورود، شناسه نشست را تغییر دهید |
| HttpOnly Cookie | از دسترسی JavaScript به کوکی جلوگیری کنید |
| SameSite Cookie | از حملات CSRF جلوگیری کنید |
| Secure Cookie | در تولید، فقط از HTTPS استفاده کنید |
| زمان انقضا | برای نشست‌ها زمان انقضای مناسب تعیین کنید |
